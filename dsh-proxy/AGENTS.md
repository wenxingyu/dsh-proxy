# AGENTS.md

Standing orders for this repository. The product contract lives in [README.zh.md](README.zh.md) / [README.md](README.md); these rules govern how the repo is changed.

## Layout

- `src/` — TypeScript source. `src/proxy.ts` is the pure-node proxy core (native Basic Auth gate, HTTP + WebSocket forwarding, Host/Origin alignment, polyfill injection) with **no cordis dependency**; `src/controller.ts` is the proxy controller (effective options = cordis base + persisted overlay, start/stop/restart, status/update/start/stop verbs, persistence to `$DSH_HOME/dsh-proxy.json`); `src/index.ts` is the cordis plugin entry (Config schema, effect lifecycle, the `/api/dsh-proxy` exact route on Connection's shared `/api` channel); `src/auth.ts` is the login gate's core (server-held sessions, per-source throttling, audit events — no HTTP), `src/audit.ts` the append-only trail, `src/security.ts` the persisted transport policy, `src/loginpage.ts` the self-contained login form, and `src/netaccess.ts` the access-mode/forwarded-header rule; `src/session.ts` / `src/settings.ts` / `src/contract.ts` are pure, unit-tested helpers and the shared wire contract; `src/polyfill.ts` is the randomUUID shim; `src/client/` is the browser half: the settings section (`SettingsSection.tsx`), the frame-wide per-page-load exposure notice (`LanExposureNotice.tsx`, registered into the shared `shell.overlay` seat), plus locales, styles, transport, and the plugin body. Authentication is a login page with a server-side session cookie (TLS, loopback, and cleartext by default), with the native Basic dialog as an explicit `cleartextAuth: 'basic'` alternative (see the access-mode rule below).
- `lib/` — committed build artifacts. `lib/index.cjs` is the fully self-contained host bundle the profile loads (schemastery, http-proxy, dsh-home-paths bundled inline; `@deepseek-ai/cordis` is type-only); `lib/client.js` is the browser bundle served at `/plugins/dsh-proxy/client.js` (only react is external). **Every source change that should be installable must rebuild and commit `lib/` in the same commit.**
- **Security posture (do not silently change):** the listener is bound exactly as configured, credentials or not — "reachable means the Basic Auth dialog, or straight in while the pair is unset". The hardening is **warning, not blocking**: `contract.ts`'s `isLanExposed()` (listener up + non-loopback host + auth off) drives the startup SECURITY WARNING, the red "open LAN access" badge and notice in the settings section, and `status.lanExposed`. A loopback-only bind and a stopped service must NOT be flagged. Turning this into a refused or degraded bind is a product decision, not a cleanup. The browser half mirrors the same rule through `status.lanExposed`: the notice is additive in `shell.overlay`, must stay non-modal (only its own card takes pointer events), and must ask the status endpoint at most once per page load. Dismissal is deliberately **not persistent** (no localStorage, no "already seen" state): the notice must return on every page load while the exposure lasts, because any remembered acknowledgement — permanent or per-day — mutes a standing security exposure. Do not add one.
- **Access modes (do not collapse them):** `netaccess.ts` resolves per-request — TLS (a trusted peer's `X-Forwarded-Proto: https`) or a loopback browser gets the **login page with a `__Host-`+`Secure` cookie**; a plain-HTTP LAN IP gets the **same login page by default** (`cleartextAuth: 'login'`) with the weaker non-`Secure` cookie variant, or the **native Basic dialog** when the operator sets `cleartextAuth: 'basic'` (a supported choice, never a silent fallback); cleartext is refused outright only under `requireTls`. The weaker cleartext cookie must stay visible: the settings card warns and the controller logs a SECURITY NOTE. Forwarded headers are believed ONLY from loopback or configured `trustedProxies` (the throttle keys on that address, so trusting them blindly would make it bypassable). A password-free configuration keeps the open behaviour: no gate, never a login form nobody can satisfy.
- **Login gate discipline:** sessions live in memory (a restart drops them) and the raw token never crosses the wire contract (`listSessions` projects a short id); login failures are uniform (no username/password distinction, constant-time compare) and throttled per source, and the audit trail records events WITHOUT credentials.
- `tests/` — vitest suites at the repo root, importing internals by relative path (`../src/*.ts`; the section spec is jsdom).
- `scripts/smoke.mjs` — live smoke test against a running DSH (`pnpm run smoke`), including a plugin-contract phase that drives the bundled `apply()` with a fake ctx (redirecting `$DSH_HOME` to a temp dir so the real persisted config is never touched); not part of `pnpm run check`.

## Build and checks

- `pnpm run typecheck`, `pnpm run test`, `pnpm run build` — all three must be green before a commit claims completion; `pnpm run check` runs them in order.
- The bundle is CommonJS on purpose: http-proxy uses dynamic `require()` calls that esbuild cannot inline into ESM output. Keep `format: 'cjs'` and the `.cjs` extension.
- The cordis loader resolves the plugin by package name through the profile's node_modules and accepts the CJS shape (`unwrapExports`); the `dsh.bundle.patch` manifest key is what makes `dsh plugin add` register the bundle.

## Commit discipline

- Conventional commits (`feat:`, `fix:`, `docs:`, `test:`, `build:`, `chore:`) with a body explaining what and why for non-trivial changes.
- One concern per commit: proxy behavior, auth, docs, build tooling, and test fixes land separately.
- Never commit credentials, `node_modules/`, or logs.

## Integration

- This plugin is named `dsh-proxy` (matching the repository) and its source lives in the `dsh-proxy/` subdirectory of the dsh-proxy repository. The repo ROOT carries a thin package manifest (name `dsh-proxy`) so the plugin installs from the repository itself: online `dsh plugin --profile <name> add github:wenxingyu/dsh-proxy#v0.1.4` (recommended) or local `dsh plugin --profile <name> add file:C:/mydata/codes/dsh-proxy` (bundle route); changes take effect on the **next `dsh web` restart**.
- The documented online install command is **pinned to a release tag, never a branch**: a user following the README must get a reproducible, verified release rather than whatever `master` happens to hold at that moment. When cutting a release, bump the tag in **all four** READMEs (root `README.md` / `README.en.md`, `dsh-proxy/README.md` / `README.zh.md`) together with the version fields, and keep this line in step.
- Dev type sources come from the npm registry, pinned to the versions the current harness (`@deepseek-ai/dsh@0.1.5-rc.2`) ships internally: `@deepseek-ai/cordis@^4.0.2`, `@deepseek-ai/schemastery@^3.18.2`, the `@deepseek-ai/dsh-*` packages at exact `0.1.5-rc.2`. Two packages do not follow the harness: `@deepseek-ai/dsh-client-runtime` is pinned to its own newest published version, `0.1.1-rc.2` — the harness no longer bundles it (it was split into `dsh-client-web` / `dsh-client-store` / `dsh-client-modules`), so its exact pin has to come from the registry's `next` line because its `latest` dist-tag is stale at `0.0.1-rc.1`; `@deepseek-ai/dsh-client-ui-layout` is type-only and exists to declare the `shell.overlay` seat. When the harness version moves, bump the harness-following pins to the new harness's bundled versions, re-check `dsh-client-runtime` against its own newest publish, and re-run `pnpm install` to fix API drift.
- The upstream port defaults to `ctx.webServer.port` (the web app's real bound port) when `upstreamPort` is 0; the plugin injects `webServer` so that value is always available before `apply` runs.
- Listen failures (e.g. EADDRINUSE when another dsh-proxy holds 3081) are logged loudly but must **never** fail the web app's boot.
